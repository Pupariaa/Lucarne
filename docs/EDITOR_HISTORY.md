# Studio editor UX history

Historical, changelog-style log of Lucarne Studio's (the `editor/` web app) UI/UX evolution. Unlike [UI_ROADMAP.md](./UI_ROADMAP.md) (a forward-looking backlog), everything below describes work that has already shipped — kept here as a dated record of what changed and why, not as a list of open tasks. For current editor usage, see [EDITOR.md](./EDITOR.md).

---

## Studio UX (responsive, onboarding, feedback, a11y)

- **Responsive (tablet)**: topbar slots move into a **More** menu by breakpoint; `#dock` becomes a right drawer under 1024px with toggle and auto-open on selection; Designer side panels overlay the canvas; Blueprint graph refits until the user pans/zooms; Simulate D-pad stacks under the screen on narrow widths.
- **Welcome / tour / help**: `welcome.js` first-run dialog (demo, blank, file, browser-saved projects); `tour.js` ten-step spotlight tour; `help.js` shortcut reference and doc links (`doc/#studio`, etc.); global keys `1`/`2`/`3` and `?`.
- **Feedback**: typed toasts, undo actions on destructive deletes, replace-project confirmation before Load/New/Open, Web Serial gate on Live/Flash, detailed import/export/save errors.
- **A11y & consistency**: `dialog.js` `trapFocus`, roving tabindex on mode/settings/export tabs, collapsible inspector sections with keyboard, wizard cells as buttons, DRC **Data keys** group label, Designer palette **Charts**, DRC panel SVG severity icons.

## Studio editor UX retrospective

Audit of the web editor (`editor/`) done while implementing the history/panels/Inspector/GPIO-wizard/RP2040/SPI-I2C/memory-gate/calc-keys/sim-nav pass. Each line is tagged `fixed in this pass` or `future work`.

### State, history & shortcuts

- No undo/redo existed; every mistake (accidental drag, delete, paste) was permanent. — **fixed in this pass**: coarse snapshot stack in `history.js`, wired to `markDirty(label)`, Fusion360-style horizontal bar in the topbar, `Ctrl+Z` / `Ctrl+Shift+Z` / `Ctrl+Y`.
- Widget clipboard existed but was private to `designer.js`; screens had no clipboard at all, and neither had a `Delete` key binding (only an Inspector button). — **fixed in this pass**: shared `clipboard.js` service used by both `designer.js` (widgets) and `graph.js` (screens), plus `Delete`/`Backspace` bindings tied into history.

### Inspector & panels

- `.section` cards were always expanded — a screen with many widgets/typography sub-panels produced an unmanageably tall dock. — **fixed in this pass**: `section()` now renders a collapsible accordion with per-section state persisted in `localStorage`.
- Pos/Size (x/y/w/h) inputs were squeezed to ~45px in a fixed 392px dock, text was barely legible. — **fixed in this pass**: 2×2 `geo-grid`, larger font/padding.
- `#dock` (392px), `.palette` (168px) and `.layers-panel` (210px) were hardcoded fixed widths with no way to collapse them on small screens. — **fixed in this pass**: drag-resizers + collapse toggles on all three, width/collapsed state persisted.
- Follow-up fix: the `.panel-collapse` toggle button (▶/◀) rendered off-center (inherited `.btn`'s `13px` horizontal padding inside a fixed `24px` box) and, on `#dock` specifically, toggling `.collapsed` only hid the tabs/body — the panel itself stayed at its resized width because the inline `style.width`/`style.flex` set by the resizer's `apply()` outranks a non-`!important` class rule. — **fixed**: `.panel-collapse` is now `display:flex; align-items:center; justify-content:center; padding:0`, and `#dock.collapsed`'s width/flex are `!important` (matching the pattern `.palette.collapsed`/`.layers-panel.collapsed` already used).
- Widget palette had no search — finding a widget in a long list meant scrolling. — **fixed in this pass**: filter box above `PALETTE_GROUPS`, collapses empty groups.
- No generic modal helper existed outside the export modal and `icon-picker.js` — every "are you sure?" or informational dialog would have needed its own bespoke markup. — **fixed in this pass**: `dialog.js` (`open`/`info`/`confirm`), reused by the board-feasibility gate and the GPIO wizard.
- Found while wiring the feasibility gate: several `style.color = "var(--warning)"` / `"var(--danger)"` assignments across `app.js` referenced CSS custom properties that don't exist (`style.css` only defines `--warn` / `--bad`), so those warning/error hints silently rendered in the inherited text color instead of amber/red. — **fixed in this pass** (all occurrences corrected).

### Hardware / GPIO

- GPIO assignment was fully manual, one number field at a time, with no awareness of which pins are strapping/flash/PSRAM/USB pins on a given devkit — easy to brick a board by picking GPIO0 or the flash pins. — **fixed in this pass**: `board-pinouts.js` curated pinout DB (ESP32/S2/S3/C3/P4, RP2040, RP2350) + `gpio-wizard.js` 3-step modal that auto-assigns SPI/display/I2C/touch/SD/button pins avoiding reserved pins, with a Ctrl+Z-able single history step on apply.
- Follow-up fix: `esp32c6` was promised in this pass's plan but never actually added, and no Arduino-branded board existed anywhere in `board-pinouts.js`/`boards-catalog.js`. — **fixed**: added `esp32c6` (ESP32-C6 DevKitC-1), `arduino_nano_esp32` (ESP32-S3 in the Nano form factor, sourced from Arduino's official D↔GPIO pinout table) and `arduino_nano_rp2040_connect` (RP2040 in the Nano form factor, sourced from the `arduino-pico`/`ArduinoCore-mbed` variant headers — its A4-A7 are read via the onboard NINA-W102 co-processor, not the RP2040, so they're intentionally excluded from the curated GPIO list). All three got matching `boards-catalog.js` entries (`BOARD_LABELS`, partition/flash-layout schemes, `RP_BOARDS`/`RP_SRAM_KB` for the RP one) so the Hardware tab's Board `<select>`, the feasibility gate and the wizard all agree on the same 10 board IDs. Classic AVR Arduino boards (Uno/Mega/Nano) are still intentionally not offered — not enough RAM/flash for a framebuffer UI — and the wizard's step 1 now says so explicitly instead of just silently omitting them.
- Board catalog only had ESP32 variants; no RP2040/RP2350, so anyone using the already-portable SPI display path on a Pico had to hand-edit partition/SRAM numbers. — **fixed in this pass**: `RP_CATALOG` flash-layout presets, `isRpBoard`/`defaultSramKb`/`boardFamily` helpers, PSRAM forced to 0 and SRAM defaulted correctly for RP targets.
- `initSpiBus()`/`initI2cBus()` codegen always emitted the ESP32 4-arg `SPI.begin(sclk,miso,mosi,ss)` / `Wire.begin(sda,scl,hz)` forms, which don't compile on the Philhower (RP2040/RP2350) Arduino core. — **fixed in this pass**: branch to `SPI.setSCK/TX/RX()` + `SPI.begin()` and `Wire.setSDA/SCL()` + `Wire.begin()` + `Wire.setClock()` for RP targets.
- I2C pins/clock were only ever exposed in the Hardware tab for an I2C-wired OLED; a SPI-TFT project with I2C touch (FT6336/GT9271/GT928) had no UI to set the touch controller's SDA/SCL/clock at all. — **fixed in this pass**: the I2C bus section now also appears (and is correctly labeled "shared" when both apply) whenever I2C touch is enabled, independent of display family.
- Memory/buffer overflow was warn-only (a toast), so it was possible to pick a board that could never fit the project and only find out by flashing. — **fixed in this pass**: `LucarneMemory.boardFeasibility()` runs the estimator against a candidate board/scheme, and the Board `<select>` now disables (with a tooltip reason) any board that would overflow flash/SRAM or that can't support the project's display family (e.g. MIPI-DSI on non-P4/RP), plus a confirmation dialog as a second line of defense.
- **Future work**: the curated pinout data covers one representative devkit per chip family (not every SKU/revision); users should still cross-check against their exact board's silkscreen. `board-pinouts.js` says so in its header comment and in the wizard's per-board notes, but there's no per-devkit sub-selection (e.g. "S3 DevKitC-1" vs "S3 N16R8") beyond the shared reserved-pin superset.
- **Superseded**: the editor used to expose `i2c_ft6336` / `i2c_gt9271` / `i2c_gt928` as touch controller choices even though the C++ library had no driver for any of them (`export.js` emitted a `// TODO: wire <kind> controller` stub returning `false`). Studio's Hardware settings and Design Rule Check have since been restricted to only offer what the firmware actually supports: **GT911** (MIPI-DSI only). See [HARDWARE.md](./HARDWARE.md) for the current, supported state; adding real drivers for other I2C touch ICs is tracked in [DISPLAY_ROADMAP.md](./DISPLAY_ROADMAP.md).

### Simulation input & navigation (`simulate.js`)

- Dead code: `nearestShapeInDirection` / `moveShapeFocus` / `ensureShapeFocus` / `activeShapeGroup` / `shapeGroupId` were fully superseded by the generic `buildNavTargets`/`moveNavFocus`/`nearestTargetInDirection` path but never removed; `shapeTargets()` (the *correct*, action-filtered helper) was defined but never called. — **fixed in this pass**: dead functions removed, `buildNavTargets`/`syncInputChrome` now use `shapeTargets()`.
- Only the first `menu` widget on a screen was reachable by D-pad/keyboard nav (`activeMenu()` did `.find(...)`); a screen with two menus (e.g. a sidebar + a content list) could only navigate one of them. — **fixed in this pass**: `menuNavItems()` returns every menu with items; all of them become spatial nav targets.
- Shape navigation only considered the *first* `group` encountered on the screen — a screen with two icon groups (e.g. a tab strip and a content area) made the second group's shapes completely unreachable via D-pad/keyboard, even though touch/click already worked on them via `hitWidget`. — **fixed in this pass**: all actionable shapes (any group) are now nav targets, matching the plan's "all shape groups" requirement. The per-shape `group` field is left in the schema for now (still editable in the Inspector) in case a future "enter this group" mode is added, but it's no longer used to exclude anything from keyboard/D-pad reach.
- Once a menu had focus, `Up`/`Down` would step through its items forever with no way back to spatial navigation — the only escape was `Left`/`Right`, which is not obvious. — **fixed in this pass**: stepping past the first/last item now falls through to `moveNavFocus()`, so `Up` at the top item (or `Down` at the bottom item) exits the menu toward whatever's spatially above/below it.
- The rotary `encoder` input type was entirely aliased to the same 4-direction D-pad model as `buttons` in the simulator, even though the firmware's `EncoderInput::update()` (`src/ui/LucarneInput.cpp`) models it very differently: quadrature rotation → `next()`/`prev()`, short button press → `select()`, **long press (≥500ms) → `back()`**, and there is no Left/Right or dedicated Back pin at all. A project designed against the simulator's 6-button model would behave unexpectedly different on real encoder hardware. — **fixed in this pass**: the Simulate d-pad now switches to a `dpad-encoder` layout (hides Left/Right and the standalone Back button, matching the 3-pin `{a,b,btn}` schema), `Left`/`Right` input is ignored outright for encoder projects, and the `OK` button now distinguishes short-press (`select()`) from a ≥500ms long-press (`back()`) to mirror the firmware exactly.
- **Future work**: "stream" graph widgets only animate when `paint()` is invoked (any state change, the splash timer, or the animated-emoji `requestAnimationFrame` loop) — there is no generic per-frame ticker, so a screen with only a stream graph and no other animated content will look static in Simulate until something else triggers a repaint. Not touched in this pass to avoid scope creep into a general "always-on preview redraw" change; worth revisiting together with a future performance pass (see *Performance & architecture* in [UI_ROADMAP.md](./UI_ROADMAP.md)).
- **Future work**: `hitWidget()` (touch hit-testing) still uses the widget's raw authored `w.h` for a `menu`'s hit box, while `widgetBounds()` (spatial keyboard/D-pad nav) computes the menu's height from `rowHeight * items.length`. They can disagree if a menu's authored height doesn't match its actual rendered row count. Predates this pass; not fixed here since it's a touch-input-only cosmetic edge case, not a nav-model gap.

### Data / calculated keys

- There was no way to derive one key from others (e.g. `Watts = Voltage * Current`) — every widget had to bind to a key that something else (simulate.js or the firmware) wrote to directly. — **fixed in this pass**: new `calc` key kind (`calc-keys.js`) with a `+ - * / ( )` formula grammar, reference/cycle validation surfaced in the Data tab, live recompute in `simulate.js`'s paint loop, and a generated `recomputeCalcs(ui)` firmware function (call once per `loop()`, before `ui.update()`).
- **Future work**: the formula grammar intentionally stops at `+ - * / ( )` (per the plan's "at minimum" scoping) — no `min`/`max`/`abs`/conditionals. Extend `calc-keys.js`'s parser/`toCpp` if that's needed later; the dependency-graph/cycle-detection/topo-order plumbing already generalizes to more operators.

### Live Preview flashing

- There was no way to get the `LucarneLivePreview.ino` receiver onto a board without opening the Arduino IDE, picking the right board settings, and compiling by hand — a lot of friction just to try the "Live" button once. — **fixed in this pass**: `esptool-js` (v0.6.1) vendored as a single bundled `esptool-js.js` (esbuild IIFE, `window.LucarneEsptool` — same vendoring pattern as `apng-js.js`), plus a new `flash.js` wizard ("Flash receiver" button next to Live) that requests a Web Serial port, syncs/detects the chip, and writes a precompiled receiver image with progress feedback.
- Two presets are shipped under `editor/firmware-bin/` (`manifest.json` + per-preset `bootloader.bin`/`partitions.bin`/`app.bin`, a shared `boot_app0.bin`), both ESP32-S3 (the only chip the receiver targets, since it needs native USB CDC): `esp32s3-st7789` (generic 240×280 SPI panel) and `esp32s3-st7796` (320×480 SPI panel, OPI PSRAM). Compiled with `arduino-cli` (`esp32:esp32` core 3.3.10) directly against this repo via `--library .`, no separate library install needed to reproduce.
- The wizard shows an informational note when the chosen preset's baked-in fallback pins differ from the project's Hardware tab pins — not a blocker, since (see below) the receiver now reconfigures itself to the project's actual pins automatically once Studio connects.
- **Future work**: only two presets exist because those are the only two Live Preview sketches in `examples/`. Adding more curated board+display combos means adding the sketch, compiling it with `arduino-cli`, and appending an entry to `editor/firmware-bin/manifest.json` — no code changes needed. RP2040/RP2350 aren't offered here since `LucarneLivePreview.h`'s protocol comments assume ESP32-S3 native USB CDC; a UART-based receiver variant would be needed first.

### Live Preview — runtime GPIO (any MCU, any wiring)

- Pins/driver for the receiver were compile-time — `examples/LucarnePreview*.ino` baked in specific CS/DC/RST/SPI pins per sketch, so the same binary only worked with one exact wiring, and the "Flash receiver" wizard's curated presets were the only way to get GPIOs that matched a given project. — **fixed in this pass**: `LucarneLivePreview.h` gained a new `HWCONFIG` (0x07) message type, handled directly in the existing `feed()`/`onComplete()` state machine (same pattern as the pre-existing `SETUP` message) rather than a separate blocking pre-boot receiver — a blocking wait was considered first but rejected because it races the host: if the board is already running when the browser's "Live" click opens the port, a boot-time timeout window would already have expired and the connection would silently fall back to whatever pins were compiled in. Instead, the sketch calls `preview.setReconfigureHandler(fn)` once at boot; `fn` just re-runs `Display::begin()` with the pins/SPI options from the packet and returns success/failure, which `LivePreview` ACKs. Since this is handled inside the always-running `update()` loop (not a boot-only phase), it works correctly however long the board has already been powered on.
- `editor/live.js` gained `sendHwConfig(cfg)`, encoding the same 19-byte payload (`cs/dc/rst/mosi/miso/sclk/bl` int8, `spiHz` u32, `spiMode`/`colorOrder`/`invert`/`panelW`/`panelH`/`rotation`) the firmware decodes, and waiting for the ACK — guarded by a small idle-wait so it doesn't collide with an in-flight frame's own ACK wait (both share the single-packet-in-flight assumption `live.js` already made for frames).
- `app.js`'s `toggleLive()` now calls `sendLiveHwConfig()` right after `connect()` (before the first `sendLiveSetup()`/frame), and every Hardware-tab pin/SPI-mode/color-order/invert field and the Board `<select>` also call it live if already connected, so GPIO edits apply immediately without reconnecting. Gated to `family === "spi_rgb"` (the only family `DisplayPins`/`DisplayOptions` — and therefore this protocol message — cover); OLED/matrix/MIPI-DSI projects don't send it (no live-preview receiver exists for those families yet).
- `examples/LucarnePreview.ino` (ST7789) and `examples/LucarnePreviewST7796.ino` (ST7796/PSRAM) updated: they still `display.begin()` once at boot with hardcoded pins (so the sketch is testable stand-alone / matches what's flashed by the wizard's presets), but that's now just a fallback — `onReconfigure()` re-runs `display.begin()` with whatever Studio sends, and `preview.setReconfigureHandler(onReconfigure)` wires it in.
- This makes "any MCU" mostly a compilation concern, not a protocol one: the sketch itself no longer hardcodes wiring, so compiling `LucarnePreview.ino` for a different board (ESP32, ESP32-C3/C6, RP2040/RP2350 — anything `Lucarne.h`'s `ST7789`/`ST7796` drivers already support) and flashing it by any means (Arduino IDE, `arduino-cli`, not just this editor's wizard) still gets correct GPIOs from the same "Live" flow, no recompile-per-wiring needed. The browser **auto-flash wizard** itself is unchanged in scope — see the two presets above — since expanding it to every chip family needs a compiled binary per target, which is a separate `arduino-cli`/toolchain effort, not a protocol limitation.
- **Future work**: `HWCONFIG` only carries the `DisplayPins`/`DisplayOptions` fields (SPI TFT family) — OLED (I2C), HD44780 (parallel), and MIPI-DSI projects have no live-preview receiver sketch at all yet, so there's nothing to reconfigure for them regardless of this change.

### Export rewrite — one-click `.ino`, plain-language summary

- Exporting only ever produced headers (`Projet.h`, `Projet_setup.h`, optional `LucarneUserConfig.h`) — turning that into a working sketch meant hand-writing `setup()`/`loop()` (SPI/I2C init order, `display.begin()`, `projet::build(ui)`, `attachInput`, keyboard config, the `update()` pair) from scratch, reading library headers to get the call signatures right. — **fixed in this pass**: `export.js`'s `buildInoSketch()` generates a ready-to-compile `.ino` (bus init, `display.begin()` with the exported pins/options, `projet::build`/`attachInput`, `ui.configureKeyboard`, PSRAM `BufferMemory` when the board has it, commented placeholders for sensor/callback/calc-key code) and `buildAll()` puts it first in the Headers tab so it's the first thing exported.
- The export modal only ever showed a byte-size toast — there was no in-editor explanation of what to do with the generated files (rename the `.ino`? where do the SD assets go?). — **fixed in this pass**: `buildExportSummaryHtml()` renders a short "what to do next" block above the file list (rename `<Sketch>.ino` and its folder to match; where the `assets/` folder needs to end up per `SD_MANIFEST.txt`/`VOLUME_MANIFEST.txt`) instead of only a transient toast.
- **Future work**: `buildInoSketch()` only generates a sketch for `spi_rgb` and `mipi_dsi` (`if (family !== "spi_rgb" && family !== "mipi_dsi") return null;`) — `oled_mono` and `matrix_lcd` projects get no `.ino` at all and fall back to the "open `Projet.h`, copy the commented recipe" message in the export summary, even though the function already has a half-built `oled_mono` branch further down (dead code behind that early guard). Predates this pass; worth either extending the guard or removing the dead branch next time this is touched.

### Asset storage restrictions

- **Superseded**: the Assets tab used to present **Web** as an image storage choice even though no HTTP loader exists in the firmware. Studio's asset-storage picker no longer offers **Web**; see [ASSETS.md](./ASSETS.md#web-storage--not-available) for the current state and [UI_ROADMAP.md](./UI_ROADMAP.md) for the tracked follow-up if a real network loader is ever prioritized.
